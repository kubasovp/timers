## 1. Назначение документа

Этот документ описывает функциональные требования к desktop-приложению, объединяющему:

* помодоро-таймеры;
* произвольные кастомные таймеры;
* одноразовые и повторяющиеся напоминания;
* локальное хранение настроек, пресетов, истории и расписаний.

Документ нужен для:

* фиксации границ MVP;
* согласования сценариев использования;
* декомпозиции задач разработки;
* последующего проектирования UX/UI и архитектуры;
* проверки готовности приложения к ежедневному использованию.

---

## 2. Краткое описание продукта

Приложение помогает пользователю управлять короткими временными сценариями в течение дня: сфокусированная работа, перерывы, бытовые таймеры, регулярные напоминания и личные ритуалы.

Основная идея: один локальный desktop-инструмент вместо трёх отдельных приложений — помодоро, таймера и напоминалки.

Приложение работает локально, без регистрации, сервера и облачной синхронизации.

---

## 3. Цели продукта

### 3.1. Основные цели

* Дать пользователю быстрый способ запускать помодоро-сессии.
* Позволить создавать произвольные таймеры под разные задачи.
* Позволить создавать простые напоминания без календарного оверхеда.
* Обеспечить надёжное срабатывание таймеров и напоминаний в desktop-среде.
* Хранить пользовательские данные локально.

### 3.2. Вторичные цели

* Поддержать ежедневные рабочие сценарии: фокус, перерывы, разминка, вода, бытовые задачи.
* Реализовать повторное использование завершённых таймеров.
* (FUTURE) Дать пользователю историю завершённых фокус-сессий
* Обеспечить первичную поддержку Linux и Windows, с последующим расширением на macOS.

---

## 4. Не-цели MVP

В MVP не входят:

* аккаунты пользователей;
* облачная синхронизация;
* мобильные приложения;
* командная работа;
* интеграция с Google Calendar / Яндекс.Календарём / Outlook;
* сложная аналитика продуктивности;
* подписки и платёжная модель;
* AI-функции;
* веб-версия;
* публичный маркетплейс пресетов.

## 6. Пользовательские роли

### 6.1. Обычный пользователь

Единственная роль в MVP.

Пользователь может:

* запускать помодоро;
* запускать произвольные таймеры;
* создавать и редактировать пресеты;
* создавать и редактировать напоминания;
* получать уведомления;
* просматривать базовую историю завершённых сессий;
* настраивать поведение приложения.

---

## 7. Основные пользовательские сценарии

### 7.1. Запуск помодоро-сессии

Пользователь открывает приложение, выбирает помодоро-профиль и запускает рабочую сессию.

Приложение показывает:

* оставшееся время;
* текущий этап: работа / короткий перерыв / длинный перерыв;
* номер цикла;
* кнопки управления: pause, resume, stop, skip.

После завершения этапа приложение показывает уведомление и предлагает перейти к следующему этапу.

### 7.2. Запуск кастомного таймера

Пользователь выбирает готовый пресет или вводит длительность вручную.

Примеры:

* 5 минут;
* 10 минут;
* 15 минут;
* 25 минут;
* 45 минут;
* 60 минут;
* пользовательская длительность.

После запуска приложение отсчитывает время и уведомляет пользователя по завершении.

### 7.3. Создание напоминания

Пользователь создаёт напоминание с текстом и временем срабатывания.

Типы напоминаний для MVP:

* одноразовое;
* ежедневное;
* интервальное, например каждые 60 минут.

После наступления времени приложение показывает системное уведомление.

### 7.4. Работа после сна или перезапуска приложения

Если компьютер уснул, приложение было закрыто или зависло, после восстановления оно должно пересчитать актуальное состояние по абсолютному времени.

Приложение не должно полагаться только на `setInterval`.

Ключевой принцип:

* хранить `startedAt`, `duration`, `endsAt`;
* вычислять оставшееся время как `endsAt - now`;
* корректно обрабатывать уже истёкшие таймеры и напоминания.

### 7.5. Получение пропущенных напоминаний

Если напоминание должно было сработать, пока приложение было закрыто, при следующем запуске приложение должно определить пропущенное событие.

Поведение MVP:

* показать список пропущенных напоминаний;
* пересчитать `nextAt` для повторяющихся напоминаний;
* не создавать бесконечную серию уведомлений за все пропущенные интервалы.

## 8. Функциональные требования

## 8.1. Помодоро

### F-POM-001 — Профили помодоро

Пользователь должен иметь возможность создавать и редактировать профили помодоро.

Профиль содержит:

* название;
* длительность рабочей сессии;
* длительность короткого перерыва;
* длительность длинного перерыва;
* количество рабочих сессий до длинного перерыва.

Acceptance criteria:

* пользователь может создать новый профиль;
* пользователь может изменить существующий профиль;
* пользователь может удалить профиль, если он не используется активной сессией;
* приложение содержит дефолтный профиль, например 25 / 5 / 15 / 4.

---

### F-POM-002 — Запуск помодоро

Пользователь должен иметь возможность запустить помодоро-сессию из выбранного профиля.

Acceptance criteria:

* после запуска отображается активный этап;
* отображается оставшееся время;
* пользователь видит, работа это или перерыв;
* приложение сохраняет состояние активной сессии локально.

---

### F-POM-003 — Управление помодоро-сессией

Пользователь должен иметь возможность управлять активной помодоро-сессией.

Действия:

* pause;
* resume;
* stop;
* skip current stage.

Acceptance criteria:

* pause останавливает уменьшение оставшегося времени;
* resume продолжает отсчёт;
* stop завершает текущую сессию со статусом `cancelled`;
* skip завершает текущий этап и переводит пользователя к следующему этапу.

---

### F-POM-004 — Завершение этапа

После завершения рабочего этапа или перерыва приложение должно уведомить пользователя.

Acceptance criteria:

* показывается системное уведомление;
* в приложении отображается состояние завершённого этапа;
* пользователь может вручную запустить следующий этап;
* опционально в настройках можно включить автозапуск следующего этапа.

---

## 8.2. Кастомные таймеры

### F-TMR-001 — Быстрый запуск таймера

Пользователь должен иметь возможность быстро запустить таймер на произвольную длительность.

Acceptance criteria:

* пользователь может ввести часы, минуты, секунды;
* приложение валидирует длительность;
* таймер нельзя запустить с нулевой или отрицательной длительностью;
* после запуска отображается оставшееся время.

---

### F-TMR-002 — Пресеты таймеров

Пользователь должен иметь возможность создавать пресеты таймеров.

Пресет содержит:

* название;
* длительность;
* опциональное описание;
* опциональную категорию.

Acceptance criteria:

* пользователь может создать пресет;
* пользователь может запустить таймер из пресета;
* пользователь может изменить пресет;
* пользователь может удалить пресет.

---

### F-TMR-003 — Управление активным таймером

Пользователь должен иметь возможность управлять активным кастомным таймером.

Действия:

* pause;
* resume;
* stop;
* restart.

Acceptance criteria:

* pause/resume работают без потери точности;
* stop завершает таймер без уведомления о завершении;
* restart запускает таймер заново с исходной длительностью.

---

### F-TMR-004 — Завершение кастомного таймера

После истечения кастомного таймера приложение должно уведомить пользователя.

Acceptance criteria:

* показывается системное уведомление;
* приложение отображает завершённое состояние;
* пользователь может быстро перезапустить таймер;
* завершение может быть записано в историю, если включена соответствующая настройка.

---

## 8.3. Напоминания

### F-REM-001 — Создание одноразового напоминания

Пользователь должен иметь возможность создать одноразовое напоминание.

Напоминание содержит:

* заголовок;
* опциональное описание;
* дату и время срабатывания;
* статус enabled / disabled.

Acceptance criteria:

* пользователь может создать напоминание на будущую дату;
* приложение не позволяет создать напоминание без заголовка;
* приложение предупреждает, если время уже прошло;
* после срабатывания одноразовое напоминание становится завершённым или неактивным.

---

### F-REM-002 — Создание ежедневного напоминания

Пользователь должен иметь возможность создать ежедневное напоминание.

Acceptance criteria:

* пользователь указывает время дня;
* приложение рассчитывает ближайшее `nextAt`;
* после срабатывания `nextAt` переносится на следующий день;
* пользователь может отключить напоминание без удаления.

---

### F-REM-003 — Создание интервального напоминания

Пользователь должен иметь возможность создать напоминание, повторяющееся через заданный интервал.

Примеры:

* каждые 30 минут;
* каждый час;
* каждые 2 часа.

Acceptance criteria:

* пользователь задаёт интервал;
* интервал должен быть больше минимально допустимого значения;
* после срабатывания приложение рассчитывает следующий `nextAt`;
* приложение не должно спамить уведомлениями после долгого простоя.

---

### F-REM-004 — Управление напоминаниями

Пользователь должен иметь возможность управлять списком напоминаний.

Действия:

* создать;
* изменить;
* включить;
* отключить;
* удалить;
* отметить выполненным;
* отложить.

Acceptance criteria:

* список показывает активные и неактивные напоминания;
* пользователь может быстро отключить напоминание;
* удаление требует подтверждения или undo;
* snooze переносит напоминание на выбранный интервал.

---

### F-REM-005 — Пропущенные напоминания

Приложение должно корректно обрабатывать напоминания, время которых наступило, пока приложение было закрыто.

Acceptance criteria:

* при запуске приложение определяет просроченные напоминания;
* пользователь видит понятное сообщение о пропущенных напоминаниях;
* для повторяющихся напоминаний рассчитывается следующий актуальный `nextAt`;
* приложение не показывает десятки уведомлений за каждое пропущенное повторение.

---

## 8.4. Уведомления

### F-NOT-001 — Системные уведомления

Приложение должно показывать системные уведомления при завершении таймеров и наступлении напоминаний.

Acceptance criteria:

* уведомление содержит заголовок;
* уведомление содержит краткий текст;
* уведомление показывается поверх обычной работы пользователя согласно правилам

## 8.7. Поведение окна и системного трея

### F-WIN-001 — Поведение кнопки закрытия (X)

Приложение должно по-разному обрабатывать закрытие окна в зависимости от платформы.

Поведение:

* Windows / macOS:

  * клик по "X" скрывает окно (hide) и оставляет приложение активным в системном трее;
  * при первом таком действии показывается кратковременная подсказка о том, что приложение продолжает работать в трее.

* Linux (MVP):

  * клик по "X" завершает приложение;
  * если есть активные таймеры или напоминания, показывается подтверждение выхода.

Acceptance criteria:

* пользователь не сталкивается с модальными окнами при обычном закрытии на Windows/macOS;
* на Linux пользователь получает подтверждение выхода только при наличии активных сущностей;
* поведение соответствует ожиданиям платформы.

---

### F-WIN-002 — Системный трей

Приложение должно использовать системный трей на Windows и macOS.

Функции трея:

* отображение иконки приложения;
* открытие главного окна по клику;
* контекстное меню.

Минимальный состав меню:

* Open;
* Pause / Resume (если есть активный таймер);
* Quit.

Acceptance criteria:

* пользователь может восстановить окно из трея;
* действия в меню работают корректно;
* состояние активного таймера может быть изменено из трея (опционально для MVP).

---

### F-WIN-003 — Выход из приложения (Quit)

При явном выходе из приложения через меню трея или аналогичный механизм поведение должно зависеть от наличия активных таймеров или напоминаний.

Поведение:

* если нет активных таймеров и напоминаний:

  * приложение закрывается без дополнительных действий;

* если есть активные таймеры или напоминания:

  * показывается подтверждение выхода с предупреждением, что уведомления не будут показаны, пока приложение закрыто.

Acceptance criteria:

* пользователь может отменить выход;
* текст предупреждения не содержит лишней технической информации;
* предупреждение не показывается, если оно не требуется.

---

### F-WIN-004 — Подсказка о работе в трее

При первом скрытии окна в трей приложение должно показать кратковременную подсказку.

Пример поведения:

* toast/tooltip с текстом вида: "App is still running in the system tray";
* подсказка исчезает автоматически;
* подсказка показывается только один раз.

Acceptance criteria:

* пользователь понимает, что приложение не завершено;
* подсказка не повторяется при каждом закрытии.

---

### F-WIN-005 — Ограничения для Linux (MVP)

В MVP версия для Linux не должна использовать системный трей по умолчанию.

Поведение:

* приложение не сворачивается в трей;
* настройка "minimize to tray" отсутствует;
* закрытие окна завершает приложение с учётом правил F-WIN-001.

Acceptance criteria:

* поведение предсказуемо для пользователей Linux;
* отсутствуют зависимости от нестабильной поддержки трея в разных DE;
* функциональность трея может быть добавлена в будущих версиях.
