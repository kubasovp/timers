# ADR-001: Выбор desktop-shell — Tauri

Status: Accepted  
Owner: github.com/kubasovp  
Date (UTC): 2026-05-06

## Context

Приложение Timers для MVP должно быть кроссплатформенным desktop-приложением (Linux/Windows), локальным, без облачного backend, с фокусом на надёжную работу таймеров и напоминаний при умеренном потреблении ресурсов.

Ключевые факторы выбора:
- низкий runtime-overhead для утилитарного приложения (таймер/напоминалка);
- достаточный контроль над системными API (уведомления, окно, трей, жизненный цикл);
- скорость разработки для frontend-разработки на привычном стеке;
- перспектива расширения на macOS в следующих версиях.

## Considered Options

1. **Tauri (Rust + WebView)**
2. **Electron (Chromium + Node.js)**
3. **Flutter Desktop (Dart)**
4. **GTK/libadwaita**
5. **Qt**

## Decision

Выбираем **Tauri** как основной desktop-shell для MVP.

Обоснование выбора относительно альтернатив:
- **Electron:** зрелый и удобный для быстрого старта, но архитектурно тяжелее (встроенные Chromium и Node.js), что выглядит избыточно для таймера/напоминалки.
- **Flutter:** рабочий кроссплатформенный вариант, но требует отдельного стека (Dart, иная UI-модель) без явной выгоды для текущей задачи.
- **GTK/libadwaita:** сильный выбор для GNOME/Linux-first сценария, но менее нейтрален как кроссплатформенный продуктовый baseline.
- **Qt:** мощная платформа, но для MVP личного таймера/фокуса вероятен избыточный уровень сложности.

## Consequences

### Positive
- Более лёгкая архитектура рантайма относительно Electron для данного класса приложения.
- Хорошая совместимость с текущим frontend-подходом (UI на web-стеке).
- Доступ к системным функциям через host-слой без необходимости встраивать полный Chromium+Node runtime.

### Negative / Trade-offs
- Порог входа в Rust-часть выше, чем чисто JS-подход.
- Экосистема и шаблоны интеграций в среднем менее «массовые», чем у Electron.
