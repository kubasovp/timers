# ADR-002: Time Semantics for Reminders (timezone/DST)

Status: Accepted (MVP scope + future extension)
Owner: github.com/kubasovp
Date (UTC): 2026-05-07

## Context

Для напоминаний есть два валидных пользовательских сценария:
1. Личное «повседневное» время (например, вода в 10:00 по местному времени пользователя).
2. Время, привязанное к конкретной локации/таймзоне (например, событие по времени определённого региона).

Требуется политика, устойчивая к:
- смене timezone пользователем;
- переходам DST;
- долгому сну устройства и перезапускам.

## Considered Options

1. **Только local-floating time** (ежедневные события следуют текущей локальной TZ устройства).
2. **Только fixed-zone time** (каждое правило жёстко привязано к IANA timezone).
3. **Гибридная модель**: режим выбирается на уровне напоминания (local-floating по умолчанию + optional fixed-zone).

## Decision

Принимается двухэтапная политика:
- **MVP:** только `local-floating` для ежедневных напоминаний.
- **Post-MVP:** optional `fixed-zone` с явным выбором IANA timezone на уровне напоминания.

Правила исполнения:
- DST spring-forward (локального времени не существует): перенос на ближайшее валидное локальное время.
- DST fall-back (локальное время двусмысленно): выбирать первое вхождение времени.
- Напоминание должно срабатывать один раз на локальную календарную дату (без дублей в fall-back).
- При смене timezone устройства:
  - `local-floating` пересчитывается в новой локальной timezone;
  - `fixed-zone` (post-MVP) остаётся привязанным к выбранной IANA timezone.

## Consequences

### Positive
- MVP упрощается: меньше сложных UX-веток и меньше рисков в реализации.
- Для повседневного сценария (локальное время пользователя) поведение ожидаемо и прозрачно.
- Есть совместимый путь расширения до `fixed-zone` без ломки доменной модели.

### Negative / Trade-offs
- Сценарии "жёстко по времени конкретной зоны" откладываются до post-MVP.
- Требуется аккуратная обработка DST boundary даже в local-floating.
- Увеличивается объём тестов (DST boundaries, timezone switches, reconcile).

### Notes for implementation
- Хранить `time_semantics` (`local_floating` | `fixed_zone`).
- Для `fixed_zone` хранить `timezone_id` (IANA), например `Europe/Berlin`.
- `nextAt` всегда материализовать в UTC для движка планирования, сохраняя исходные правила для пересчёта.
